## 2. 기능 요구사항 (Functional Requirements)

### FR1. 사용자 관리 (P0)

| ID | 요구사항 | 화면 |
|---|---|---|
| FR1.1 | 사용자는 ID/PW 로 로그인할 수 있다 | 로그인 |
| FR1.2 | 신규 사용자는 회원가입 신청 후 관리자 승인을 거쳐 활성화된다 | 회원가입 / 사용자 승인 |
| FR1.3 | 본인 정보(이름·연락처·이메일·비밀번호) 를 수정할 수 있다 | 본인 정보 |
| FR1.4 | 비밀번호 재설정(찾기) 절차를 제공한다 | 비밀번호 찾기 |
| FR1.5 | 관리자는 모든 사용자 정보를 조회/수정/삭제할 수 있다 | 사용자 관리 |
| FR1.6 | 사용자 권한은 admin / user 두 단계로 구분된다 | (전 화면) |

**상세 규칙**
- ID: 영소문자 시작, 영소문자+숫자 5~16자
- 비밀번호: 8자 이상, 특수문자 1개 이상 (`~!@#$%^&*()=+`)
- 회원가입 시 개인정보 수집·이용 동의 필수
- 세션 만료: 비활성 30분 후 자동 로그아웃

### FR2. API 등록 및 관리 (P0)

| ID | 요구사항 |
|---|---|
| FR2.1 | 관리자는 신규 API 를 등록할 수 있다 (API번호 자동 채번) |
| FR2.2 | API 등록 시 요청경로 중복 검증을 수행한다 |
| FR2.3 | API 등록 시 데이터소스, HTTP 메서드, 그룹, 상태, 인증여부, 문서 노출 여부를 지정한다 |
| FR2.4 | API 의 SQL 소스를 등록한다 (Monaco Editor) |
| FR2.5 | API 의 입력 파라미터(이름, 타입, 필수, 마스킹 규칙) 를 정의한다 |
| FR2.6 | API 의 응답 컬럼(이름, 타입, 마스킹 규칙) 을 정의한다 |
| FR2.7 | 등록된 API 를 검색·수정·삭제할 수 있다 |
| FR2.8 | API 등록 시 SQL 구문 검증(EXPLAIN PLAN) 을 자동 수행한다 |
| FR2.9 | API 의 SQL 은 화이트리스트 검증(SELECT/INSERT/UPDATE/DELETE/CALL) 을 통과해야 등록 가능 |
| FR2.10 | 사용자는 등록된 API 를 조회 가능 (수정 불가) |

### FR3. 데이터소스 관리 (P0)

| ID | 요구사항 |
|---|---|
| FR3.1 | 관리자는 데이터소스(DB 커넥션) 를 등록할 수 있다 |
| FR3.2 | 데이터소스 등록 항목: 데이터소스명, DB 종류(Oracle/PG/MySQL), JDBC URL, 사용자, 암호, 풀 사이즈 |
| FR3.3 | 등록 시 연결 테스트 버튼 제공 |
| FR3.4 | 데이터소스 수정 시 기존 풀은 graceful drain, 새 풀로 hot-swap (재시작 없음) |
| FR3.5 | 데이터소스 삭제 시 사용 중인 API 가 있으면 차단 |
| FR3.6 | 데이터소스 비밀번호는 MetaDB 에 암호화 저장 (Vault Transit 또는 AES-256) |

### FR4. 연계시스템 관리 (P0)

| ID | 요구사항 |
|---|---|
| FR4.1 | 관리자는 외부 호출 시스템(연계시스템) 을 등록한다 |
| FR4.2 | 등록 시 인증키(certification-key) 자동 발급 (HMAC SHA-256 기반) |
| FR4.3 | 허용 IP 다중 등록 가능 (CIDR 표기 지원) |
| FR4.4 | 사용기간(시작일시 ~ 종료일시) 설정 |
| FR4.5 | 연계시스템에 매핑할 API 다중 선택 |
| FR4.6 | 연계시스템 수정/삭제, 인증키 재발급 가능 |
| FR4.7 | 사용자는 본인이 등록된 연계시스템만 조회 가능 |

### FR5. 외부 호출 게이트웨이 (P0 — 핵심)

| ID | 요구사항 |
|---|---|
| FR5.1 | `https://api.donga.ac.kr/api/{요청경로}` 패턴으로 외부 호출 수신 |
| FR5.2 | 호출 헤더 `certification-key` 검증 |
| FR5.3 | 호출 측 IP 가 연계시스템 허용 IP 에 포함되는지 검증 |
| FR5.4 | 인증키 사용기간 내 호출인지 검증 |
| FR5.5 | 호출 API 가 해당 연계시스템에 매핑되어 있는지 검증 |
| FR5.6 | 위 4단 검증 실패 시 적절한 4xx 응답 + 사유 로깅 |
| FR5.7 | 검증 통과 시 등록 SQL 을 데이터소스에서 실행 |
| FR5.8 | 파라미터 바인딩은 Prepared Statement 강제 (문자열 결합 금지) |
| FR5.9 | 응답 컬럼별 마스킹 룰 적용 |
| FR5.10 | Content-Type: `application/x-www-form-urlencoded` (default), `application/json` 둘 다 수신 |
| FR5.11 | Accept: `application/json` (default), `application/xml` 둘 다 응답 가능 |
| FR5.12 | 쿼리 타임아웃 기본 10초, API 별 override 가능 |

### FR6. 실시간 모니터링 (P0)

| ID | 요구사항 |
|---|---|
| FR6.1 | 호출 이력은 Redis Stream 또는 인메모리 큐를 거쳐 비동기 적재 |
| FR6.2 | 모니터링 화면에서 호출 이력 검색 (기간, 인증키, API, 응답코드, IP 조건) |
| FR6.3 | 호출당 컬럼: 호출시각, 인증키, 클라이언트 IP, 요청경로, HTTP 메서드, 파라미터(요약), 응답코드, 응답시간(ms) |
| FR6.4 | 응답코드별 통계 차트 (시간대별 막대그래프) |
| FR6.5 | 사용자 본인이 매핑된 연계시스템의 이력만 조회 가능 (admin 전체 조회) |
| FR6.6 | 이력은 최소 90일 보관, 그 이후 외부 OLAP/OpenSearch 로 이관 |

### FR7. API 문서 (P0)

| ID | 요구사항 |
|---|---|
| FR7.1 | `Document 표시 여부 = TRUE` 인 API 만 노출 |
| FR7.2 | 좌측 트리(API 그룹별), 우측 상세(파라미터/응답/예시) 형태 |
| FR7.3 | 호출 예시(curl, Postman, JSON 응답) 자동 생성 |
| FR7.4 | OpenAPI 3 스펙 다운로드(`/openapi.json`) 제공 |
| FR7.5 | 비로그인 사용자도 접근 가능 (단, 인증키는 노출 금지) |

### FR8. 승인 워크플로우 (P1)

| ID | 요구사항 |
|---|---|

| FR8.2 | 관리자는 신청 목록을 조회·승인·반려한다 |
| FR8.3 | 승인 시 해당 사용자가 속한 연계시스템에 API 가 자동 매핑됨 |

## 3. 비기능 요구사항 (Non-Functional Requirements)

### NFR1. 성능 (Performance)

| ID | 요구사항 | 측정 |
|---|---|---|
| NFR1.1 | 외부 호출 응답 시간 p95 < 500ms (DB 쿼리 시간 제외 < 50ms) | Prometheus histogram |
| NFR1.2 | 동시 처리량 ≥ 1,000 RPS / Pod | K6 부하 테스트 |
| NFR1.3 | API 등록 화면 응답 < 1초 | Lighthouse |
| NFR1.4 | 데이터소스 hot-swap 시 in-flight 쿼리 영향 없음 | Graceful drain 검증 |
| NFR1.5 | 호출 이력 적재 지연 < 5초 (큐 → DB) | Custom metric |

### NFR2. 보안 (Security)

| ID | 요구사항 |
|---|---|
| NFR2.1 | 모든 외부 통신은 TLS 1.2 이상 (HTTPS) |
| NFR2.2 | 비밀번호는 bcrypt (cost 12) 해시 저장 |
| NFR2.3 | 데이터소스 비밀번호는 Vault Transit 으로 암호화 |
| NFR2.4 | API Key 는 HMAC SHA-256 기반 발급, MetaDB 에 해시 저장 |
| NFR2.5 | SQL 인젝션 방어: Prepared Statement 강제, DDL/DCL 차단 |
| NFR2.6 | 화면 인증: JWT (15분 만료, refresh 토큰 24시간) |
| NFR2.7 | OWASP Top 10 통과 (XSS, CSRF, IDOR 등) |
| NFR2.8 | 감사 로그: 모든 변경 작업에 REGID/REGDT/REGIP/REGMENU/REGPGM 자동 기록 |

> 상세는 [09 보안 및 인증 설계서](09_보안_및_인증_설계서.md) 참조.

### NFR3. 가용성 (Availability)

| ID | 요구사항 |
|---|---|
| NFR3.1 | 서비스 가용성 99.9% (월 다운타임 < 43.2분) |
| NFR3.2 | Backend Pod 최소 2개 (HPA 2~10) |
| NFR3.3 | PodDisruptionBudget minAvailable=1 (노드 드레인 시 무중단) |
| NFR3.4 | Liveness/Readiness probe 분리, 데이터소스 장애를 readiness 에 반영 금지 |
| NFR3.5 | Graceful Shutdown: SIGTERM 후 60초 내 정상 종료 |
| NFR3.6 | RTO ≤ 5분, RPO ≤ 1분 (장애 복구 시간/데이터 손실 한계) |

### NFR4. 확장성 (Scalability)

| ID | 요구사항 |
|---|---|
| NFR4.1 | Horizontal Pod Autoscaler: CPU 70% 또는 RPS 기반 |
| NFR4.2 | 데이터소스 추가는 무중단 (재시작 불필요) |
| NFR4.3 | 호출 이력은 90일 후 OLAP/OpenSearch 이관 (MetaDB 스키마 부담 분리) |
| NFR4.4 | Redis 캐시: 인증키·API 메타·OpenAPI 스펙 캐싱 (TTL 5분) |
| NFR4.5 | 스테이트리스 백엔드 (세션 외부화) |

### NFR5. 유지보수성 (Maintainability)

| ID | 요구사항 |
|---|---|
| NFR5.1 | 단위 테스트 커버리지 ≥ 80% (백엔드 서비스 계층) |
| NFR5.2 | 통합 테스트: H2 또는 Testcontainers (Oracle XE) |
| NFR5.3 | 코드 리뷰 필수 (PR 1명 이상 승인) |
| NFR5.4 | 정적 분석: SonarQube (선택), ESLint, Spotless |
| NFR5.5 | 모든 API 응답은 표준 형식 `{success, data, message, errorCode}` |
| NFR5.6 | 로그는 구조화(JSON), trace-id 포함 |

### NFR6. 호환성 (Compatibility)

|---|---|

## 4. 사용자 시나리오 (Use Cases)

### UC1. 신규 API 등록 (관리자)
1. 관리자 로그인
2. API 메뉴 → 등록 버튼
3. API 명, 그룹, 메서드, 요청경로 입력 (중복 확인)
4. 데이터소스 선택
5. SQL 작성 (Monaco Editor)
6. 파라미터/응답 컬럼 정의
7. 마스킹 룰 입력
8. 저장 → EXPLAIN 검증 → 성공 시 등록

### UC2. 외부 시스템에서 API 호출 (외부 시스템)
1. 발급받은 인증키와 등록 IP 로 `GET /api/sample-user-info?id=1` 호출
2. 게이트웨이가 4단 검증 (key, IP, 사용기간, API 매핑)
3. 검증 통과 → 매핑된 데이터소스에서 SQL 실행
4. 결과 마스킹 후 JSON 응답
5. 호출 이력 비동기 적재

### UC3. 신규 데이터소스 추가 (DBA + 관리자)
1. DBA 가 신규 Oracle 인스턴스 준비
2. 관리자가 데이터소스 등록 화면에서 입력 + 연결 테스트
3. 저장 → 백엔드가 새 HikariCP 풀 생성, 라우팅 맵에 추가 (재시작 없음)
4. 해당 데이터소스를 사용하는 API 등록

### UC4. 사용자가 API 사용 신청 → 관리자 승인 (사용자/관리자)
1. 사용자가 API 목록 화면에서 사용 신청
2. 관리자가 승인 화면에서 검토 후 승인
3. 자동으로 사용자 소속 연계시스템에 매핑
4. 사용자에게 이메일 통보
