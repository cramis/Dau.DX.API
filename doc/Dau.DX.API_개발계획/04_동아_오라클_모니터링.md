# 04. 동아 Oracle 19c 기반 실시간 모니터링 PRD (초안)

> 본 문서는 Mockup 의 인메모리 큐(`lib/mockHistory.ts`) 를 Phase 2 의 Oracle 19c 영속 저장으로 옮기는 설계 결정을 정리한다. [`open-questions.md` B4](open-questions.md) 를 닫는 데 사용된다.

---

## 0. 한 페이지 요약

- **무엇을**: gateway 호출이 발생할 때마다 한 row 씩 Oracle `call_history` 테이블에 적재. 모니터링 화면은 5초 폴링으로 KPI/차트/상위영향API 를 계산.
- **왜 Oracle**: 동아대 환경에 19c 가 이미 운영 중(시드의 `DAU-CORE-PROD`). 별도 시계열 DB 도입 부담 없이 분당 1k~10k 호출 규모는 충분히 처리 가능.
- **언제 시작**: Mockup 사인오프 직후. 백엔드 스택([`open-questions A`](open-questions.md) ) 이 픽스되면 즉시 적용.
- **블로커**: 사내 Oracle 의 tablespace 발급 + 사용 가능한 옵션(Partitioning / Advanced Compression) 라이선스 확인.

## 2. 데이터 모델

### 2-1. 메인 테이블 — `call_history`

```sql
CREATE TABLE call_history (
  seq          NUMBER GENERATED ALWAYS AS IDENTITY,
  called_at    TIMESTAMP(3) NOT NULL,
  ext_sys_id   VARCHAR2(20),                    -- nullable: 익명 호출 시 NULL
  api_no       VARCHAR2(20),                    -- nullable: API_NOT_FOUND 시 NULL
  req_path     VARCHAR2(128) NOT NULL,
  method       VARCHAR2(10)  NOT NULL,
  client_ip    VARCHAR2(45),                    -- IPv6 대비
  trace_id     VARCHAR2(40)  NOT NULL,
  param_json   CLOB,                            -- 마스킹 후 저장 (PIPA)
  status_code  NUMBER(3)     NOT NULL,
  error_code   VARCHAR2(40),                    -- nullable: 정상이면 NULL
  elapsed_ms   NUMBER        NOT NULL,
  CONSTRAINT pk_call_history PRIMARY KEY (called_at, seq)
)
PARTITION BY RANGE (called_at)
INTERVAL (NUMTODSINTERVAL(1, 'DAY'))
( PARTITION p_init VALUES LESS THAN (TIMESTAMP '2026-01-01 00:00:00') )
ENABLE ROW MOVEMENT;
```

**핵심 결정**:
- **PK = (called_at, seq)** — 파티션 키 포함 PK. 단일 `seq` PK 는 GLOBAL 인덱스 강제로 파티션 drop 비용↑. composite PK 가 LOCAL 보장.
- **`INTERVAL (1 DAY)`** — DBA 개입 0. 자정마다 새 파티션 자동 생성.
- **`COMPRESS FOR OLTP`** 옵션 — Advanced Compression 라이선스 있으면 추가 (40~60% 압축, INSERT 미세 손해). 없으면 생략.

### 2-2. 인덱스 (모두 LOCAL)

```sql
CREATE INDEX ix_call_at      ON call_history (called_at)              LOCAL;
CREATE INDEX ix_call_api     ON call_history (api_no, called_at)      LOCAL;
CREATE INDEX ix_call_status  ON call_history (status_code, called_at) LOCAL;
CREATE INDEX ix_call_trace   ON call_history (trace_id)               LOCAL;
CREATE INDEX ix_call_ext     ON call_history (ext_sys_id, called_at)  LOCAL;
```

- 모두 LOCAL — 파티션 drop 시 인덱스도 함께 사라져 운영 부담 0.
- `ix_call_trace` 만 단일 컬럼 (단건 lookup).
- 다른 4종은 모두 (조건컬럼, called_at) 복합 — range partition pruning 후 인덱스 range scan.

### 2-3. 사전 집계 MV — `mv_call_stats_1m` (선택)

분당 60k+ 호출 시 hot 테이블 직접 GROUP BY 가 느려지면 도입:

```sql
CREATE MATERIALIZED VIEW LOG ON call_history
  WITH ROWID, SEQUENCE
  (called_at, api_no, status_code, elapsed_ms)
  INCLUDING NEW VALUES;

CREATE MATERIALIZED VIEW mv_call_stats_1m
  BUILD IMMEDIATE
  REFRESH FAST ON COMMIT
AS
SELECT
  TRUNC(called_at, 'MI')                                     AS minute_bucket,
  api_no,
  COUNT(*)                                                   AS cnt,
  SUM(CASE WHEN status_code BETWEEN 200 AND 299 THEN 1 END)  AS ok_cnt,
  SUM(CASE WHEN status_code BETWEEN 400 AND 499 THEN 1 END)  AS err4xx_cnt,
  SUM(CASE WHEN status_code >= 500              THEN 1 END)  AS err5xx_cnt,
  AVG(elapsed_ms)                                            AS avg_ms,
  MAX(elapsed_ms)                                            AS max_ms
FROM call_history
GROUP BY TRUNC(called_at, 'MI'), api_no;
```

**주의**:
- `REFRESH FAST ON COMMIT` 은 INSERT TX 에 약 1~3% 오버헤드.
- `PERCENTILE_DISC` 는 증분 불가 → MV 에 못 넣음. p95 는 hot 테이블 직접 조회 유지.
- 부담되면 `REFRESH ON DEMAND` + DBMS_SCHEDULER 로 매분 갱신.

## 3. 쿼리 패턴 — Mockup 의 라이브 화면 4종 매핑

### 3-1. 4 KPI ([Mockup `statsSnapshot` 대응](../../mockup/lib/mockHistory.ts))

```sql
SELECT
  COUNT(*)                                                        AS total,
  SUM(CASE WHEN status_code BETWEEN 200 AND 299 THEN 1 END)       AS ok_cnt,
  SUM(CASE WHEN status_code >= 400              THEN 1 END)       AS err_cnt,
  SUM(CASE WHEN status_code >= 500              THEN 1 END)       AS err5xx_cnt,
  PERCENTILE_DISC(0.95) WITHIN GROUP (ORDER BY elapsed_ms)        AS p95
FROM call_history
WHERE called_at >= SYSTIMESTAMP - INTERVAL '10' MINUTE;
```

- 마지막 10~60분만 보면 **항상 한 파티션(오늘) 안** → 부분 스캔.
- `RESULT_CACHE` 힌트 추가 시 5초 폴링 중복 부하 캐싱.

### 3-2. 3-line 분당 차트

```sql
SELECT
  TRUNC(called_at, 'MI')                                          AS minute_bucket,
  SUM(CASE WHEN status_code BETWEEN 200 AND 299 THEN 1 END)       AS s2xx,
  SUM(CASE WHEN status_code BETWEEN 400 AND 499 THEN 1 END)       AS s4xx,
  SUM(CASE WHEN status_code >= 500              THEN 1 END)       AS s5xx
FROM call_history
WHERE called_at >= SYSTIMESTAMP - INTERVAL '30' MINUTE
GROUP BY TRUNC(called_at, 'MI')
ORDER BY minute_bucket;
```

- 30 row 만 반환. 백엔드에서 빈 분(missing minute) 0 으로 채워 응답.

### 3-3. 상위 영향 API

```sql
SELECT
  api_no,
  COUNT(*)                                                        AS cnt,
  PERCENTILE_DISC(0.95) WITHIN GROUP (ORDER BY elapsed_ms)        AS p95,
  SUM(CASE WHEN status_code >= 400 THEN 1 END)                    AS err_cnt,
  ROUND(100 * SUM(CASE WHEN status_code >= 400 THEN 1 END) / COUNT(*), 1)
                                                                  AS err_rate
FROM call_history
WHERE called_at >= SYSTIMESTAMP - INTERVAL '30' MINUTE
GROUP BY api_no
ORDER BY err_rate DESC, cnt DESC
FETCH FIRST 8 ROWS ONLY;
```

가장 빈번한 errorCode (별도 윈도우 함수):

```sql
WITH ranked AS (
  SELECT api_no, error_code, COUNT(*) AS c,
         ROW_NUMBER() OVER (PARTITION BY api_no ORDER BY COUNT(*) DESC) rn
  FROM call_history
  WHERE called_at >= SYSTIMESTAMP - INTERVAL '30' MINUTE
    AND error_code IS NOT NULL
  GROUP BY api_no, error_code
)
SELECT api_no, error_code FROM ranked WHERE rn = 1;
```

### 3-4. trace-id 단건 (현재 `/monitoring/logs/[traceId]`)

```sql
SELECT * FROM call_history WHERE trace_id = :traceId;
```

`ix_call_trace` 를 통해 모든 파티션을 cross-partition lookup. 단건 회수 < 10ms.

### 3-5. 자동 인시던트 감지 (현재 Mockup 의 `errors5xx >= 3` 룰)

`/monitoring` 대시보드 헤더에서 5초 폴링 중 같은 KPI 쿼리 결과로 평가. 별도 쿼리 불필요. 정식 알림 규칙은 `/monitoring/rules` 의 evaluator 가 따로 처리.

## 4. 수집 경로

### 4-1. 권장 — (A) 동기 INSERT

```java
// gateway 응답 직전, 같은 TX 또는 별도 TX 로 INSERT
PreparedStatement ps = conn.prepareStatement(
  "INSERT INTO call_history " +
  "(called_at, ext_sys_id, api_no, req_path, method, client_ip, trace_id, " +
  " param_json, status_code, error_code, elapsed_ms) " +
  "VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)"
);
// bind 변수 11개 — literal SQL 절대 금지 (SOFT_PARSE 폭증)
```

- **응답시간 영향**: < 1ms (인덱스 5종 갱신 포함).
- **손실 위험**: 0 (TX commit 보장).
- **동시성**: HikariCP 기본 풀로 충분.

### 4-2. 부하 늘면 — (B) 비동기 배치

분당 10k+ 도달 시 BlockingQueue + 별도 worker 가 100건씩 batch INSERT:

```java
PreparedStatement ps = conn.prepareStatement("INSERT ...");
for (CallHistory c : batch) {
  ps.setTimestamp(1, Timestamp.valueOf(c.calledAt));
  // ...
  ps.addBatch();
}
ps.executeBatch();   // 분당 60k+ 도 단일 인스턴스로 견딤
```

- 응답시간 영향 0.
- 앱 crash 시 큐 손실 가능 → in-memory 큐 사이즈 제한 + 셧다운 훅으로 flush.

### 4-3. 무손실 보장 필요 시 — (C) Oracle Advanced Queueing

Oracle 내장 메시지 큐(AQ) 를 사용하면 ENQUEUE 가 트랜잭션 안에서 보장됨:

```sql
DBMS_AQADM.CREATE_QUEUE_TABLE(...);
DBMS_AQADM.CREATE_QUEUE(...);
-- gateway → ENQUEUE
-- DBMS_SCHEDULER job → DEQUEUE → INSERT call_history
```

- 외부 큐(Kafka 등) 없이 Oracle 만으로 무손실. DBA 친화적.
- 단, AQ 운영 경험 필요.

**기본 결정**: **(A) 시작 → 분당 10k 넘으면 (B) → 무손실 요구 시 (C)**.

## 5. 보존 정책

| 단계 | 기간 | 저장소 | 용도 |
|---|---|---|---|
| **hot** | 0~7일 | `call_history` 원본 | trace 단건 검색, 최근 통계 |
| **warm** | 7~30일 | `mv_call_stats_1m` (분 rollup) | 24시간 / 7일 KPI |
| **cold** | 30~365일 | `mv_call_stats_1h` (시 rollup, 압축) | 월간 분석 |
| **drop** | 1년+ | — | PIPA 보존기간 만료. 자동 drop |

### 자동 drop 잡 (예시)

```sql
-- 매일 새벽 3시 — 7일 지난 파티션 drop
BEGIN
  DBMS_SCHEDULER.CREATE_JOB(
    job_name        => 'job_drop_old_call_history',
    job_type        => 'PLSQL_BLOCK',
    job_action      => q'[
      DECLARE
        v_cutoff DATE := TRUNC(SYSDATE) - 7;
      BEGIN
        FOR p IN (SELECT partition_name, high_value
                  FROM user_tab_partitions
                  WHERE table_name = 'CALL_HISTORY')
        LOOP
          -- high_value 가 cutoff 이전인 파티션만 drop
          -- (실제로는 EXECUTE IMMEDIATE 로 high_value 평가 필요)
          NULL;
        END LOOP;
      END;
    ]',
    start_date      => SYSTIMESTAMP,
    repeat_interval => 'FREQ=DAILY;BYHOUR=3',
    enabled         => TRUE
  );
END;
```

또는 운영 단순성 위해 **`DBMS_REDEFINITION` + ASSM tablespace 자동 회수** 사용.

## 6. 실시간 푸시

| 방식 | 추천도 | Oracle 측 |
|---|---|---|
| **5초 폴링** (현재 Mockup 패턴) | ★★★ 시작 기본 | 5초마다 SELECT 5종 |
| **SSE (Server-Sent Events)** | ★★ 인시던트 알림 채널만 | Spring `SseEmitter` 가 1초마다 새 5xx row SELECT 후 push |
| **Oracle CQN** | ★ 비추 | 분당 수천 INSERT 환경엔 callback storm |
| **WebSocket** | 0 (현재 불필요) | — |

**기본 결정**: 폴링 유지. 인시던트만 SSE 추가 검토 (Phase 2 #2).

## 7. 운영 주의

| 항목 | 권장 |
|---|---|
| **Tablespace** | `TS_DXAPI_MON` 전용. 비즈니스 데이터와 분리. AUTOALLOCATE + ASSM |
| **PDB 분리** | 가능하면 `DXAPI_MON` PDB. 모니터링 부하가 비즈니스 DB 에 영향 0 |
| **UNDO_RETENTION** | 짧게 (15분) — 대량 INSERT/DROP PARTITION 워크로드 |
| **Bind 변수** | 100% 강제. literal SQL 발견 시 EXPLAIN PLAN 으로 SOFT_PARSE 카운트 모니터 |
| **PIPA 마스킹** | `param_json` 저장 전 `apiResp.maskRule` 정책으로 마스킹. mockup 의 `MASK_RULES` 와 동일 정책 적용 |
| **Audit** | 관리자 SELECT 행위는 별도 audit log (Oracle Unified Auditing) — `select_call_history` policy |
| **Stat collection** | `DBMS_STATS.GATHER_TABLE_STATS` 를 매일 1회 (파티션별 incremental) |

## 8. 성능 ballpark (Oracle 19c, 일반 운영 사양 — 16 core / 32GB / SSD)

| 부하 | 권장 패턴 | CPU | INSERT 응답 영향 | 1년 데이터량 |
|---|---|---|---|---|
| 분당 1k (≈ 16 TPS) | (A) 동기 | < 5% | < 1ms | ~5억 row, 100GB |
| 분당 10k (≈ 167 TPS) | (A) 동기 | 10~20% | 1~3ms | ~50억 row, 1TB |
| 분당 60k (≈ 1000 TPS) | (B) 배치 권장 | 30~50% | 0 (큐) | ~300억 row, 6TB |
| 분당 100k+ | (C) AQ 또는 외부 큐 | — | — | 별도 분리 |

**대학 Dau.DX.API 1년차 가정**: 분당 1k 미달 → **(A) 동기 INSERT + 7일 hot 만으로 충분**. 사전 집계 MV 없이도 단일 파티션 GROUP BY 로 30분 윈도우 KPI < 100ms.
