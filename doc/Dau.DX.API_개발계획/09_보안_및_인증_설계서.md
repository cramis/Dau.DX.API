## 1. 보안 모델 개요

### 1.1 두 가지 인증 흐름

```
┌──────────────────────────────────────────────────────────────┐
│  1. 사용자 인증 (관리자 콘솔용)                                  │
│     ID/PW → bcrypt 검증 → JWT (Access 15분, Refresh 24시간)    │
│     /admin/** 접근 시 Authorization: Bearer 토큰              │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  2. 외부 호출 인증 (게이트웨이용)                                 │
│     certification-key 헤더 + 4단 검증                         │
│     /api/** 진입 시 ApiKeyAuthFilter 가 처리                  │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 보안 원칙
- **Defense in Depth**: 다층 방어 (Ingress → Filter → Service → DB)
- **Zero Trust**: 모든 요청 검증 (내부 통신도 mTLS 권장)
- **Least Privilege**: 사용자/Pod/DB 계정 최소 권한
- **Auditability**: 모든 변경에 감사 로그
- **Secret Externalization**: 평문 시크릿 코드/git 에 금지

## 2. 사용자 인증 (JWT)

### 2.1 토큰 사양

| 토큰 | 만료 | 저장 위치 | 용도 |
|---|---|---|---|
| **Access Token** | 15분 | 메모리 (브라우저), HttpOnly Cookie 권장 | API 호출 |
| **Refresh Token** | 24시간 | HttpOnly + Secure Cookie | Access 갱신 |

**Access Token Claims**
```json
{
  "sub": "admin01",
  "role": "ADMIN",
  "name": "관리자",
  "iat": 1715155200,
  "exp": 1715156100,
  "jti": "uuid-v4"
}
```

### 2.2 비밀번호 정책
- bcrypt cost 12 해시 저장 (PASSWORD_HASH 컬럼)
- 최소 8자, 특수문자 1개 이상 (`~!@#$%^&*()=+`)
- 5회 실패 → 1분 잠금 (LOGIN_FAIL_CNT)
- 90일마다 변경 권고 (강제 아님)
- 동일 ID 의 마지막 5개 비밀번호 재사용 차단

### 2.3 로그인 흐름
```
1. POST /admin/auth/login { userId, password }
2. 백엔드: USR_USER_M 조회 → bcrypt.matches(password, hash)
3. 성공: Access + Refresh 토큰 발급, LOGIN_FAIL_CNT 초기화
4. 실패: LOGIN_FAIL_CNT++, 5회 → 잠금
5. 응답: { accessToken, refreshToken, user }
```

### 2.4 Refresh 회전 (Rotation)
- Refresh 사용 시 즉시 신규 Refresh 발급, 기존 토큰 무효화
- Refresh 토큰은 Redis 에 jti 단위 저장 (revoke 가능)

### 2.5 로그아웃
- Refresh 토큰 즉시 폐기 (Redis 에서 삭제)
- 모든 기기 로그아웃: 사용자 ID 의 모든 jti 폐기

## 3. 외부 호출 인증 (API Key)

### 3.1 API Key 발급
```
신규 연계시스템 등록
  ↓
백엔드:
  1. UUID v4 + 타임스탬프 → HMAC SHA-256 with master key (Vault)
  2. 평문 키 = "{prefix-8자}-{나머지}"  예: "AKAD0001-XXXX-YYYY-ZZZZ"
  3. MetaDB 에 해시 저장 (CERT_KEY_HASH = bcrypt(평문, cost 10))
  4. CERT_KEY_PREFIX 만 평문 저장 (조회용)
  ↓
화면에 평문 키 1회 표시 (이후 재조회 불가)
```

### 3.2 4단 검증 흐름

```
1. 헤더 추출
   certification-key: "AKAD0001-XXXX-YYYY-ZZZZ"
   ↓
2. Redis 캐시 조회 (key prefix → ext_sys_id)
   캐시 미스 시 MetaDB 조회 + 캐시 등록 (TTL 5분)
   ↓
3. CERT_KEY_HASH 검증 (bcrypt)
   ↓
4. 4단 검증 (모두 통과해야 함)
   ① IP ∈ ALLOWED_IPS (CIDR 매칭)
   ② SYSDATE ∈ [USE_BEGIN_DT, USE_END_DT]
   ③ STATUS_CD = 'ACTIVE'
   ④ requestPath ∈ EXT_SYS_API_MAP_M (해당 시스템에 매핑된 API)
```

### 3.3 IP 화이트리스트
- **CIDR 표기 지원**: `10.0.0.0/24`, `192.168.1.5/32`
- **IPv6 지원**: `0:0:0:0:0:0:0:1` → `127.0.0.1` 정규화
- **X-Forwarded-For** 헤더 신뢰 (Ingress 가 부여)
- 신뢰 가능한 프록시 목록만 헤더 신뢰

### 3.4 API Key 재발급
- `POST /admin/ext-systems/{id}/regenerate-key`
- 신규 키 발급 + 즉시 화면 표시
- 기존 키는 즉시 무효화 (Redis 캐시 + MetaDB 모두)
- 외부 시스템에 통보 (이메일)

## 4. SQL 인젝션 방어

### 4.1 Prepared Statement 강제
- 등록 SQL 의 `#{param}` 표기 → MyBatis/JdbcTemplate 의 placeholder 자동 변환
- 문자열 결합 (`'`+param+`'`) 금지 — 코드 리뷰에서 차단
- 동적 컬럼명/테이블명은 화이트리스트로만 허용

### 4.2 SQL 화이트리스트
```java
private static final Pattern ALLOWED = Pattern.compile(
    "^\\s*(SELECT|INSERT|UPDATE|DELETE|MERGE|BEGIN|CALL)\\b",
    Pattern.CASE_INSENSITIVE);

private static final Set<String> BLOCKED_TOKENS = Set.of(
    "DROP", "TRUNCATE", "ALTER", "CREATE", "GRANT", "REVOKE",
    "EXECUTE IMMEDIATE", "DBMS_", "UTL_", "SYS."
);
```
- 등록 시 위 검증 통과해야 저장
- 등록 시 EXPLAIN PLAN (Oracle) 실행 → 구문 검증

### 4.3 쿼리 타임아웃
- 기본 10초, API 별 override 가능
- HikariCP `setQueryTimeout()` + Statement timeout
- 초과 시 `408 QUERY_TIMEOUT` 반환

### 4.4 결과 행 수 제한
- 기본 10,000 행 제한 (API 별 override)
- 초과 시 응답에 `truncated: true` 표시

## 5. 데이터 마스킹

### 5.1 마스킹 룰 (`MASKING_RULE_CD`)

| 룰 | 패턴 | 예시 | 정규식 처리 |
|---|---|---|---|
| `name` | 첫글자 외 `*` | `홍**` | `s/(.).*/$1**/` |
| `phone` | 가운데 4자리 | `010-****-5678` | `(\d{3})-\d{4}-(\d{4})` → `$1-****-$2` |
| `email` | `@` 앞 절반 | `a**@xxx.com` | `^(.).*?(@.*)$` → `$1**$2` |
| `rrn` | 뒷 7자리 | `990101-1******` | `(\d{6})-\d{7}` → `$1-1******` |
| `card` | 가운데 8자 | `1234-****-****-3456` | |
| `addr` | 동/번지 마스킹 | `서울시 ... ***` | 룰 기반 |

### 5.2 마스킹 적용 시점
- 백엔드 응답 직렬화 직전 (`MaskingService.apply`)
- 외부 호출 게이트웨이 응답에만 적용 (관리자 콘솔 조회는 미적용 또는 별도 정책)
- 호출 이력 (`PARAMS_JSON`) 도 마스킹 적용 후 저장

### 5.3 사용자 정의 마스킹
- Phase 2 이후: 정규식 입력 가능 (admin 만)

## 6. 시크릿 관리

### 6.1 시크릿 종류

| 시크릿 | 저장 위치 | 접근 방식 |
|---|---|---|
| MetaDB 비밀번호 | Vault (KV) | External Secrets Operator → K8s Secret |
| 사용자 등록 DB 비밀번호 | MetaDB (Vault Transit 암호화) | 백엔드가 복호화 후 HikariCP 설정 |
| JWT 서명 키 (HS256) | Vault (KV) | ESO → K8s Secret → env 변수 |
| API Key 마스터 시드 (HMAC) | Vault (KV) | 동상 |
| Redis 비밀번호 | Vault (KV) | 동상 |
| 이메일 SMTP 비밀번호 | Vault (KV) | 동상 |

### 6.2 ESO (External Secrets Operator) 흐름
```
[Vault] hashicorp/vault
   ↑ 동기화
[ESO] ExternalSecret CR
   ↓ 생성
[K8s Secret] dau-dx-api-secrets
   ↓ envFrom 또는 mount
[Pod] env 변수
```

### 6.3 ExternalSecret 예시
```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: dau-dx-api-secrets
  namespace: dau-dx-api-prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: dau-dx-api-secrets
  data:
    - secretKey: META_DB_PASSWORD
      remoteRef: { key: dau-dx-api/prod/meta-db, property: password }
    - secretKey: JWT_SIGNING_KEY
      remoteRef: { key: dau-dx-api/prod/jwt, property: signing-key }
```

### 6.4 Vault Transit (사용자 DB 비밀번호)
- 등록 시: `vault write transit/encrypt/dau-dx-api plaintext={base64}` → ciphertext 저장
- 사용 시: `vault write transit/decrypt/dau-dx-api ciphertext={...}` → 평문 복호화 후 풀 생성에 사용
- 키 회전: 주기적 `transit/keys/.../rotate`, ciphertext 자동 재암호화 가능

## 7. 통신 보안

### 7.1 외부 통신 (TLS)
- 모든 외부 진입은 HTTPS (TLS 1.2+)
- 인증서: cert-manager + Let's Encrypt 또는 사내 CA
- HSTS 헤더: `Strict-Transport-Security: max-age=31536000; includeSubDomains`

### 7.2 내부 통신
- K8s 내부 Service 간 통신은 ClusterIP (사설망)
- 권장: Istio/Linkerd mTLS (Phase 2)

### 7.3 보안 헤더 (Frontend)
```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'
Permissions-Policy: geolocation=(), microphone=(), camera=()
```

### 7.4 CORS
- 백엔드 `/admin/**`: Next.js 도메인만 허용 (사실상 동일 도메인)
- 백엔드 `/api/**`: `Access-Control-Allow-Origin: *` 가능 (외부 호출 허용)

## 8. 감사 로그 (Audit Log)

### 8.1 감사 필드 (모든 마스터 테이블)

| 컬럼 | 설명 |
|---|---|
| REGID | 등록자 사용자 ID |
| REGDT | 등록일시 (TIMESTAMP) |
| REGIP | 등록자 IP |
| REGMENU | 등록 시 메뉴 ID |
| REGPGM | 등록 시 프로그램 ID |
| MODID | 수정자 |
| MODDT | 수정일시 |
| MODIP | 수정자 IP |
| MODMENU | 수정 시 메뉴 ID |
| MODPGM | 수정 시 프로그램 ID |

### 8.2 자동 주입 (Spring AOP / MyBatis Interceptor)
```java
@Aspect
@Component
public class AuditAspect {
    @Before("execution(* dau.dx.api..repo..insert*(..)) || @annotation(Auditable)")
    public void injectAudit(JoinPoint jp) {
        var ctx = AuditContext.current();  // ThreadLocal
        // entity.setRegId(ctx.userId), setRegDt(now), setRegIp(ctx.ip)...
    }
}
```

### 8.3 인증 실패 로그
- 모든 4단 검증 실패는 별도 로그 + 메트릭 (`ezapi_auth_fail_total{reason}`)
- 동일 IP 분당 10회 실패 → 자동 차단 (Redis Counter + IP block list)

## 9. OWASP Top 10 점검

| OWASP | 본 시스템 대응 |
|---|---|
| A01 Broken Access Control | JWT 권한 체크, `/admin/**` 정책, 본인 자원만 접근 |
| A02 Cryptographic Failures | TLS 1.2+, bcrypt 12, HMAC SHA-256, Vault Transit |
| A03 Injection | Prepared Statement, SQL 화이트리스트, EXPLAIN 검증 |
| A04 Insecure Design | 본 PRD 보안 모델 + 4단 검증 + Audit |
| A05 Security Misconfiguration | distroless 이미지, root 금지, 보안 헤더, 시크릿 외부화 |
| A06 Vulnerable Components | Trivy 스캔 (Harbor), Dependabot, SBOM |
| A07 Identification and Authentication Failures | JWT + Refresh 회전, 로그인 실패 잠금 |
| A08 Software and Data Integrity Failures | Cosign 이미지 서명, GitOps 변경 감사 |
| A09 Security Logging and Monitoring Failures | OTel + Loki + 인증 실패 알람 |
| A10 SSRF | 외부 호출 없음. 데이터소스 URL 화이트리스트 |

## 10. 침해 대응 (Incident Response)

| 상황 | 대응 |
|---|---|
| API Key 유출 의심 | `/admin/ext-systems/{id}/regenerate-key` → 즉시 무효화 + 통보 |
| 사용자 계정 탈취 의심 | 모든 기기 로그아웃 + 비밀번호 강제 변경 |

## 11. 보안 점검 자동화

### 11.1 CI 단계
- **컨테이너 스캔**: Trivy (Harbor), High/Critical 발견 시 fail
- **의존성 스캔**: OWASP Dependency-Check, npm audit
- **SAST**: SonarQube (선택), GitLeaks (시크릿 검출)
- **시크릿 스캔**: gitleaks pre-commit hook + Gitea Actions

### 11.2 런타임
- **K8s**: NetworkPolicy 강제, PodSecurityStandards `restricted`
- **Falco**: 비정상 시스템 콜 감지 (선택)
- **Kyverno**: 이미지 서명 강제 (Cosign), root 금지 정책

### 11.3 정기 점검
- 분기 1회 모의 침투 테스트
- 월 1회 의존성 업데이트 + 재배포
- 주 1회 감사 로그 리뷰

- GDPR/PIPA 준수 검토 (필요시)
