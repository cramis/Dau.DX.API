- [ ] 11개 화면 모두 사용자 승인

## 4. Phase 3 — 정식 개발 (M3, M4)

> 상세는 [08 본 개발 계획](08_본_개발_계획.md) 참조.

### 4.1 주차별 산출물

| 주 | 산출물 |
|---|---|
| W1 | 신규 git repo 부트스트랩, MetaDB 스키마 적용, Spring Hello-World |
| W2 | DataSourceManager + RoutingDataSource (단위 테스트 PASS) |
| W3 | GatewayController + ApiKeyAuthFilter + DynamicSqlExecutor |

| W6 | 부하 테스트 (1,000 RPS), 보안 점검 (OWASP), 통합 e2e + dev 배포 |

- 첫 실 Oracle 19c 데이터소스 1개 등록
- 샘플 API 1개 등록 후 외부 호출 시뮬레이션
- 모니터링·알람 정상 동작
- 단위 테스트 ≥ 80%, e2e ≥ 5개 PASS
- 부하 테스트 1,000 RPS / Pod, p95 < 500ms

## 5. Phase 4-6 — 안정화·이관 (M5, M6)

### 5.1 M5 (stg/prod 환경 분리, 1주)
- ezapi-gitops repo 의 stg/prod overlay 작성
- ExternalSecret CR 등록 (stg/prod 의 Vault 경로)
- Argo CD Application 추가 (stg 자동 sync, prod 수동)
- prod 배포 절차 리허설 1회

### 5.2 M6 (안정화·이관, 3주)
- 기존 EzAPI 의 API 100개 마이그레이션
  - SQL 자산 그대로 이전
  - 인증키 재발급 + 외부 시스템 통보
  - 회귀 테스트 (10개 샘플 → 100개 전체)
- 병행 운영 (기존 + 신규 양쪽 호출 가능)
- 컷오버 D-day:
  - 기존 EzAPI 의 도메인을 신규 시스템으로 전환
  - 다운타임 ≤ 30분 목표
- 컷오버 후 1주 모니터링 강화 → 안정화 선언

## 8. 변경 관리 (Change Management)

### 8.1 PRD 변경 절차
1. 변경 제안 → GitOps repo 또는 본 PRD 폴더의 PR
2. 영향 분석 (일정·범위·예산)
3. PO 승인
4. 본 문서 + 관련 문서 일괄 업데이트
5. CHANGELOG 기록

### 8.2 범위 변경 제어
- **In-Scope 추가**: PO + 아키텍트 합의 필수
- **Out-of-Scope 제거**: 자유로움 (단, 영향 분석)
- **Phase 1 → 3 동시 진행 금지**: Mockup 확정 전 backend 작업 금지
