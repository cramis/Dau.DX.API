## 1. 프로젝트 정의

### 1.1 명칭
- **공식명**: `Dau.DX.API`
- **설명형 정의**: 동아대학교 데이터 통합 플랫폼 차세대 API 게이트웨이
- **카테고리**: Self-Service Data API Platform / Multi-DB SQL-to-REST Gateway

### 1.2 한 문장 요약
> **Dau.DX.API 는 등록된 SQL/프로시저를 인증키·IP 통제 하에 REST API 로 노출하는 멀티-DB API 게이트웨이이며, 비개발자(또는 DBA) 도 SQL 만으로 표준 REST 엔드포인트를 즉시 발급할 수 있는 셀프서비스 플랫폼이다.**

### 1.3 기존 시스템과의 관계
- **기존 EzAPI**: 동아대 운영 중인 Java/Spring 기반 데이터 통합 API 서비스 (`net.ezinc.api.adm.web.*`)
- **본 프로젝트**: 기존 EzAPI 의 **재개발 (Re-development)**. 도메인·비즈니스 로직은 계승하되, 스택·아키텍처·운영 모델을 현대화.
- **이전 전략**: 기존 운영 시스템과 **병행 운영** 후 검증 완료 시 **컷오버**.

## 2. 배경 및 문제 정의

### 2.1 기존 EzAPI 의 한계
| # | 문제 | 영향 |
|---|---|---|
| P1 | 레거시 화면(JSP/Old Spring) UX | 신규 사용자 학습 곡선 高, 모바일/반응형 미지원 |
| P2 | 단일 인스턴스 운영 (스케일 아웃 어려움) | 외부 호출 스파이크 시 성능 저하 |
| P3 | 배포 수동화, 환경 분리 미약 | 배포 리스크 高, 롤백 복잡 |
| P4 | 관측성 부족 (구조화 로그/메트릭 미흡) | 장애 원인 파악 지연 |
| P5 | 동적 데이터소스 추가 시 재시작 필요 | 서비스 중단 발생 |
| P6 | API 등록 절차에 SQL 검증·EXPLAIN 자동화 미흡 | 잘못된 SQL 등록 위험 |

### 2.2 재개발 동기
- **운영 안정성 향상**: K8s 기반 다중 Pod 운영, HPA 자동 스케일, 우아한 종료
- **GitOps 도입**: Gitea Actions → Harbor → Argo CD → K8s 표준 파이프라인
- **관측성 표준화**: OpenTelemetry + Prometheus + Loki 통합
- **셀프서비스 강화**: SQL 검증·테스트·문서 자동화로 사용자 부담 경감

## 3. 핵심 도메인 모델

```
┌──────────────┐  사용  ┌──────────────────────────────┐
│  데이터소스   │◀───────│              API              │
│ (DB 커넥션)   │        │  (REST 엔드포인트 + SQL)      │
└──────────────┘        └──────────────┬───────────────┘
                                       │ 매핑(N:M)
                                       ▼
                        ┌──────────────────────────────┐
                        │         연계시스템              │
                        │  (인증키 + 허용IP + 사용기간)    │
                        └──────────────┬───────────────┘
                                       │ 사용
                                       ▼
                        ┌──────────────────────────────┐
                        │         사용자(admin/user)     │
                        └──────────────────────────────┘
```

| 엔터티 | 설명 | 주요 속성 |
|---|---|---|
| **데이터소스** | 실제 DB 접속 정보 | JDBC URL, USER, PASSWORD, 풀 사이즈, DB 종류(Oracle/PG/MySQL) |
| **API** | 외부 노출 엔드포인트 | API 번호, 요청경로, HTTP 메서드, 등록 SQL, 응답 컬럼 메타, 데이터소스 ID |
| **연계시스템** | 외부 호출 측 시스템 | 시스템명, 인증키(certification-key), 허용 IP, 사용기간, 매핑 API 목록 |
| **사용자** | 플랫폼 로그인 주체 | ID, 비밀번호, 권한(admin/user), 소속, 승인 상태 |
| **호출이력** | API 호출 로그 | 호출시각, 인증키, IP, 요청경로, 파라미터, 응답코드, 응답시간 |

> 데이터 모델 상세는 [06 데이터 모델 설계서](06_데이터_모델_설계서.md) 참조.

## 4. 핵심 목표

### 4.1 비즈니스 목표 (B-Goal)
| ID | 목표 | KPI |
|---|---|---|
| B1 | 기존 EzAPI 사용자가 신규 시스템으로 무중단 이전 | 컷오버 시 다운타임 ≤ 30분 |
| B2 | 신규 API 등록 → 외부 호출까지 소요 시간 단축 | 평균 < 30분 (현행 추정 1~2시간) |
| B3 | 셀프서비스 비율 향상 (관리자 개입 없는 등록) | 신규 API 의 70% 이상 사용자 자체 등록 |
| B4 | 호출 실패 원인 파악 시간 단축 | 평균 < 5분 (모니터링 화면) |

### 4.2 기술 목표 (T-Goal)
| ID | 목표 | KPI |
|---|---|---|
| T1 | API 응답 시간 (p95) | < 500ms (DB 쿼리 시간 제외 < 50ms) |
| T2 | 동시 처리량 | 1,000 RPS / Pod (Virtual Threads) |
| T3 | 가용성 | 99.9% (월 다운타임 < 43.2분) |
| T4 | 배포 자동화 | dev: push 후 자동, stg/prod: PR merge 후 자동/수동 |
| T5 | 관측성 | 모든 호출에 trace-id, 메트릭 7종 노출 |
| T6 | 컨테이너 콜드스타트 | < 15s (Spring Boot, Native Image 시 < 1s) |

## 5. 범위 (Scope)

### 5.1 본 프로젝트에 포함 (In-Scope)
- ✅ 관리자 콘솔 화면 12개 (로그인/회원가입/비밀번호찾기/API/데이터소스/연계시스템/모니터링/문서/승인 2종/사용자관리/본인정보)
- ✅ 외부 호출 동적 게이트웨이 (`/api/{path}`)
- ✅ 멀티-DB 데이터소스 라우팅 (Oracle 19c 우선, PG/MySQL 확장 가능)
- ✅ 인증키 + IP 화이트리스트 + 사용기간 통제
- ✅ 호출 이력 비동기 적재 + 실시간 검색
- ✅ API 문서 자동 생성 (OpenAPI 3 기반)
- ✅ 사용자 회원가입/승인 워크플로우
- ✅ CI/CD 파이프라인 (Gitea Actions, Harbor, Argo CD, K8s)
- ✅ 관측성 (메트릭/로그/트레이스)

### 5.2 본 프로젝트에서 제외 (Out-of-Scope)
- ❌ 새로운 인증 프로토콜 도입 (OAuth2/SAML 등) — 기존 인증키 모델 유지
- ❌ GraphQL 지원 — REST 만 지원
- ❌ 실시간 스트리밍 (WebSocket/SSE) API — 단일 요청-응답만 지원
- ❌ 외부 SaaS 연동 마켓플레이스 — 내부 DB 노출 한정
- ❌ 사용량 기반 과금/결제 — 내부 사용자 무료 (감사 추적은 함)
- ❌ 사용자별 SQL 편집 권한 세분화 — admin 만 SQL 작성 가능
- ❌ 멀티 테넌시 (조직별 분리 운영) — 단일 동아대 인스턴스

### 5.3 Phase 별 범위
- **Phase 1 (Mockup)**: 12개 화면 시안 + 샘플 게이트웨이 5개 (Mock 데이터)
- **Phase 3 (정식)**: 위 In-Scope 전체

## 8. 제약사항 및 가정

### 8.1 제약사항
- **DB**: Oracle 19c 사용 확정 (기존 인프라 호환). PostgreSQL/MySQL 은 Phase 3 이후 확장.
- **K8s**: 동아대 사내 클러스터 사용 (외부 클라우드 없음).
- **인증**: 기존 인증키 모델 유지 (외부 시스템과의 하위 호환성).
- **언어**: 화면 한국어 기본, 다국어는 Phase 6 이후 검토.
- **브라우저**: Chrome/Edge 최신 2개 버전, IE 미지원.

### 8.2 가정
- 동일 운영팀이 `Dau.DX.Dox`(.NET 10) 와 `Dau.DX.API`(Spring Boot) 를 동시 운영 (학습 곡선 일부 발생 수용).
- Oracle 19c MetaDB 신설 가능 (별도 스키마 또는 별도 인스턴스).
- 사내 Gitea, Harbor, Argo CD 인프라는 별도 팀이 제공 (사용 권한만 받음).
- 기존 EzAPI 의 SQL 자산은 그대로 이전 가능 (검증 후).

### 8.3 의존성
- **외부**: 사내 IDP (사용자 디렉터리), 사내 Vault, Harbor 운영 안정성.
- **내부**: MetaDB 스키마 확정, 인증키 발급 정책 확정, IP 정책 확정.
