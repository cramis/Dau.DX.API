## 1. 보안 모델 개요

### 1.1 두 가지 인증 흐름

```
┌──────────────────────────────────────────────────────────────┐
│  1. 사용자 인증 (관리자 콘솔용)                                  │
│     ID/PW → bcrypt 검증 → JWT (Access 15분, Refresh 24시간)    │
│     /admin/** 접근 시 Authorization: Bearer 토큰              │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  2. 외부 호출 인증 (게이트웨이용)                                 │
│     certification-key 헤더 + 4단 검증                         │
│     /api/** 진입 시 ApiKeyAuthFilter 가 처리                  │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 보안 원칙
- **Defense in Depth**: 다층 방어 (Ingress → Filter → Service → DB)
- **Zero Trust**: 모든 요청 검증 (내부 통신도 mTLS 권장)
- **Least Privilege**: 사용자/Pod/DB 계정 최소 권한
- **Auditability**: 모든 변경에 감사 로그
- **Secret Externalization**: 평문 시크릿 코드/git 에 금지

## 2. 사용자 인증 (JWT)

### 2.1 토큰 사양

| 토큰 | 만료 | 저장 위치 | 용도 |
|---|---|---|---|
| **Access Token** | 15분 | 메모리 (브라우저), HttpOnly Cookie 권장 | API 호출 |
| **Refresh Token** | 24시간 | HttpOnly + Secure Cookie | Access 갱신 |

**Access Token Claims**
```json
{
  "sub": "admin01",
  "role": "ADMIN",
  "name": "관리자",
  "iat": 1715155200,
  "exp": 1715156100,
  "jti": "uuid-v4"
}
```

### 2.2 비밀번호 정책
- bcrypt cost 12 해시 저장 (`PW_HASH` 컬럼)
- 최소 8자, 특수문자 1개 이상 (`~!@#$%^&*()=+`)
- 5회 실패 → 1분 잠금 (`LOGIN_FAILURE_TMCNT`)
- 90일마다 변경 권고 (강제 아님)
- 동일 ID 의 마지막 5개 비밀번호 재사용 차단

### 2.3 로그인 흐름
```
1. POST /admin/auth/login { userId, password }
2. 백엔드: DXAPI_USR_USER_M 조회 → bcrypt.matches(password, hash)
3. 성공: Access + Refresh 토큰 발급, LOGIN_FAILURE_TMCNT 초기화
4. 실패: LOGIN_FAILURE_TMCNT++, 5회 → 잠금
5. 응답: { accessToken, refreshToken, user }
```

### 2.4 Refresh 회전 (Rotation)
- Refresh 사용 시 즉시 신규 Refresh 발급, 기존 토큰 무효화
- Refresh 토큰은 Redis 에 jti 단위 저장 (revoke 가능)

### 2.5 로그아웃
- Refresh 토큰 즉시 폐기 (Redis 에서 삭제)
- 모든 기기 로그아웃: 사용자 ID 의 모든 jti 폐기

## 3. 외부 호출 인증 (API Key)

> **장기 사용 키 모델**. 단기 토큰 발급 모델(/token) 은 채택하지 않는다. cert-key 는 발급 1회 → 만료/회전까지 그대로 사용. 검증 핫패스는 **HMAC-SHA256 + Redis 캐시** 로 1,000 RPS/Pod 충족(NFR1.2).

### 3.1 API Key 발급
```
신규 연계시스템 등록
  ↓
백엔드:
  1. 32바이트 random (CSPRNG) → Base32 인코딩 → cert-key 평문 생성
  2. 평문 키 = "{prefix-8자}-{나머지}"  예: "AKAD0001-XXXXXXXX-YYYYYYYY-ZZZZZZZZ"
  3. CRTFC_KEY_HASH = HMAC-SHA256(masterSeed, plaintextKey)
       - masterSeed 는 Vault KV (`api-key/hmac-seed`) → ESO → env (API_KEY_HMAC_SEED)
       - 결정적 해시 → 매 호출마다 동일 값 비교 가능 (캐시 친화)
  4. CRTFC_KEY_DISTI_TEXT = 평문 앞 8자 (식별·조회용, 비밀 아님)
  ↓
MetaDB 저장: CRTFC_KEY_HASH (HMAC), CRTFC_KEY_DISTI_TEXT (앞 8자)
화면에 평문 키 1회 표시 (이후 재조회 불가)
```

> **bcrypt 제외 근거**. cert-key 는 매 호출 검증되는 핫패스다. bcrypt(cost 10) 은 코어당 ≈10 ops 라 1,000 RPS/Pod (NFR1.2) 와 양립 불가. bcrypt 는 사용자 비밀번호(`PW_HASH`, §2.2) 에만 한정 사용한다. cert-key 는 충분한 엔트로피(≥256bit) + masterSeed 회전으로 등가 보안을 확보한다.

### 3.2 4단 검증 흐름

```
1. 헤더 추출
   certification-key: "AKAD0001-XXXXXXXX-YYYYYYYY-ZZZZZZZZ"
   ↓
2. Redis 캐시 조회 (key 평문 자체 또는 그 SHA-256 prefix → 검증결과)
   - 적중: 검증된 EXT_SYS 메타(허용IP·기간·매핑API) + lastSeenAt 갱신
   - 미스: HMAC 계산 → MetaDB 의 CRTFC_KEY_HASH 와 동등성 비교 → 적중 시 캐시 (TTL 60s)
   ↓
3. 4단 검증 (모두 통과해야 함, AND 조건)
   ① 키 식별: CRTFC_KEY_HASH = HMAC-SHA256(masterSeed, headerKey)
   ② IP 화이트리스트: clientIp ∈ ALW_IP_ADDR_TEXT (CIDR 매칭)
   ③ 사용기간 + 활성: SYSDATE ∈ [USE_BEGIN_DT, USE_END_DT] AND STTUS_DVCD = 'ACTIVE'
                       ※ 활성여부는 사용기간 검증의 일부로 흡수, 별도 단계 아님
   ④ API 매핑: REQ_PATH ∈ DXAPI_EXT_SYS_API_MAP_M[CONTCT_SYST_ID]
```

> **단계 정의 일치성**. 02 §FR5.2~5.5, 03 §4.1, 05 §3.2, 08 §3.4.4, INDEX 도메인 모델 모두 본 4단(키·IP·사용기간·매핑) 과 일치한다. STTUS_DVCD 는 ③ 안에 흡수되어 별도 단계로 세지 않는다.

### 3.2.1 캐시 무효화 (Cache Invalidation)
- 인증키 재발급 (`POST /admin/ext-systems/{id}/regenerate-key`) → Redis `cert:{distiPrefix}:*` 일괄 삭제
- 매핑 변경 (`POST/DELETE /admin/ext-systems/{id}/apis/...`) → 해당 시스템 캐시 항목 삭제
- 시스템 비활성화 → 캐시 즉시 삭제 (TTL 만료 대기 금지)
- masterSeed 회전 → 모든 cert 캐시 flush + 신규 HMAC 으로 재계산

### 3.3 IP 화이트리스트
- **CIDR 표기 지원**: `10.0.0.0/24`, `192.168.1.5/32`
- **IPv6 지원**: `0:0:0:0:0:0:0:1` → `127.0.0.1` 정규화
- **X-Forwarded-For** 헤더 신뢰 (Ingress 가 부여)
- 신뢰 가능한 프록시 목록만 헤더 신뢰

### 3.4 API Key 재발급
- `POST /admin/ext-systems/{id}/regenerate-key`
- 신규 키 발급 + 즉시 화면 표시
- 기존 키는 즉시 무효화 (Redis 캐시 + MetaDB 모두)
- 외부 시스템에 통보 (이메일)

## 4. SQL 인젝션 방어

### 4.1 Prepared Statement 강제
- 등록 SQL 의 `#{param}` 표기 → MyBatis/JdbcTemplate 의 placeholder 자동 변환
- 문자열 결합 (`'`+param+`'`) 금지 — 코드 리뷰에서 차단
- 동적 컬럼명/테이블명은 화이트리스트로만 허용

### 4.2 SQL 화이트리스트
```java
// 첫 토큰 6종만 허용. PL/SQL anonymous block(BEGIN..END) 은 차단.
private static final Pattern ALLOWED = Pattern.compile(
    "^\\s*(SELECT|INSERT|UPDATE|DELETE|MERGE|CALL)\\b",
    Pattern.CASE_INSENSITIVE);

// 본문 어디에도 등장하면 거부.
private static final Set<String> BLOCKED_TOKENS = Set.of(
    "DROP", "TRUNCATE", "ALTER", "CREATE", "GRANT", "REVOKE",
    "BEGIN", "DECLARE", "EXECUTE IMMEDIATE",
    "DBMS_", "UTL_", "SYS.", "DBA_"
);
```

**왜 BEGIN 차단인가**. PL/SQL 익명 블록 `BEGIN ... EXECUTE IMMEDIATE 'DROP TABLE X'; END;` 는 첫 토큰 정규식만 보면 통과한다. EXECUTE IMMEDIATE 도 정규식 match 만으로는 주석/문자열 분리 실패 가능. 따라서 첫 토큰 + 본문 토큰 양쪽에서 BEGIN/DECLARE/EXECUTE IMMEDIATE 를 모두 차단한다.

**CALL 호출 정책**.
- `CALL` 로 시작하는 SQL 은 **등록된 procedure name 화이트리스트** 와 일치해야 한다.
- `DXAPI_API_DEF_M` 에 `ALLOWED_CALL_NM` 컬럼(또는 별도 `DXAPI_API_CALL_M` 테이블) 으로 등록 시점에 procedure 식별자 명시.
- 런타임 검증: `CALL\\s+([A-Z_][A-Z0-9_$.]*)\\s*\\(` 의 캡처 그룹이 화이트리스트에 있어야 통과.
- DBMS_/UTL_/SYS./DBA_ 패키지는 BLOCKED_TOKENS 로 이중 차단.

**등록 시 구문 검증**.
- DML(SELECT/INSERT/UPDATE/DELETE/MERGE) → `EXPLAIN PLAN FOR <sql>` (Oracle 19c) 으로 구문·바인딩 검증.
- CALL → `EXPLAIN PLAN` 은 빈 plan 반환 가능. 대신 `DBMS_SQL.PARSE` (DML/PLSQL 모두 지원) 를 사용해 구문만 검증하고 즉시 close.
- 검증 전용 sandbox 데이터소스에서 수행 (운영 풀 부담 회피, R13 대응).

### 4.3 쿼리 타임아웃
- 기본 10초, API 별 override 가능
- HikariCP `setQueryTimeout()` + Statement timeout
- 초과 시 `408 QUERY_TIMEOUT` 반환

### 4.4 결과 행 수 제한
- 기본 10,000 행 제한 (API 별 override)
- 초과 시 응답에 `truncated: true` 표시

## 5. 데이터 마스킹

### 5.1 마스킹 룰 (`MASK_RULE_DVCD`)

| 룰 | 패턴 | 예시 | 정규식 처리 |
|---|---|---|---|
| `name` | 첫글자 외 `*` | `홍**` | `s/(.).*/$1**/` |
| `phone` | 가운데 4자리 | `010-****-5678` | `(\d{3})-\d{4}-(\d{4})` → `$1-****-$2` |
| `email` | `@` 앞 절반 | `a**@xxx.com` | `^(.).*?(@.*)$` → `$1**$2` |
| `rrn` | 뒷 7자리 | `990101-1******` | `(\d{6})-\d{7}` → `$1-1******` |
| `card` | 가운데 8자 | `1234-****-****-3456` | |
| `addr` | 동/번지 마스킹 | `서울시 ... ***` | 룰 기반 |

### 5.2 마스킹 적용 시점
- 백엔드 응답 직렬화 직전 (`MaskingService.apply`)
- 외부 호출 게이트웨이 응답에만 적용 (관리자 콘솔 조회는 미적용 또는 별도 정책)
- 호출 이력 (`PARAM_JSON_TEXT`) 도 마스킹 적용 후 저장

### 5.3 사용자 정의 마스킹
- Phase 2 이후: 정규식 입력 가능 (admin 만)

### 5.4 stg 환경 복제 시 PII 마스킹 (운영 → stg)

10 §6.2 의 "stg = 운영 복제 DB" 정책은 PII 가 평문으로 stg 에 흘러들어가는 위험을 동반한다. **운영 → stg 복제는 마스킹 후 적재** 를 강제한다.

| 대상 컬럼 | stg 적재 시 처리 |
|---|---|
| `DXAPI_USR_USER_M.PW_HASH` | 임의 더미 bcrypt 해시로 일괄 치환 (stg 로그인은 별도 시드 계정만) |
| `DXAPI_USR_USER_M.HP_NO`, `EMAIL` | 마스킹 룰 `phone`/`email` 적용 후 적재 |
| `DXAPI_USR_EXT_SYS_M.CRTFC_KEY_HASH` | stg 전용 신규 HMAC 으로 재발급 (운영 키 절대 비유출) |
| `DXAPI_DATASOURCE_M.DB_ENC_PW` | stg 전용 Vault Transit 키로 재암호화 (운영 ciphertext 비복원) |
| `DXAPI_CALL_HIST_L.PARAM_JSON_TEXT` | 응답 마스킹 룰 그대로 적용 + 운영 PII 컬럼명에 매칭되면 전부 `***` |
| `DXAPI_CALL_HIST_L.CLIENT_IP_ADDR` | `/24` 까지만 보존 (마지막 옥텟 0) |

**복제 절차** (운영 DBA 책임).
1. 운영 RMAN export 또는 Data Pump 로 덤프 추출
2. 마스킹 변환 잡(`tools/scripts/mask-prod-to-stg.sql`) 실행 — 위 표 적용
3. 변환 검증 (PII 컬럼 sample 100행 무작위 추출하여 마스킹 적용 여부 확인)
4. stg 환경에 적재 + 스모크 테스트
5. 변환 잡의 입력 덤프는 즉시 폐기 (보존 금지)

## 6. 시크릿 관리

### 6.1 시크릿 종류

| 시크릿 | 저장 위치 | 접근 방식 |
|---|---|---|
| MetaDB 비밀번호 | Vault (KV) | External Secrets Operator → K8s Secret |
| 사용자 등록 DB 비밀번호 | MetaDB (Vault Transit 암호화) | 백엔드가 복호화 후 HikariCP 설정 |
| JWT 서명 키 (HS256) | Vault (KV) | ESO → K8s Secret → env 변수 |
| API Key 마스터 시드 (HMAC) | Vault (KV) | 동상 |
| Redis 비밀번호 | Vault (KV) | 동상 |
| 이메일 SMTP 비밀번호 | Vault (KV) | 동상 |

### 6.2 ESO (External Secrets Operator) 흐름
```
[Vault] hashicorp/vault
   ↑ 동기화
[ESO] ExternalSecret CR
   ↓ 생성
[K8s Secret] dau-dx-api-secrets
   ↓ envFrom 또는 mount
[Pod] env 변수
```

### 6.3 ExternalSecret 예시
```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: dau-dx-api-secrets
  namespace: dau-dx-api-prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: dau-dx-api-secrets
  data:
    - secretKey: META_DB_PASSWORD
      remoteRef: { key: dau-dx-api/prod/meta-db, property: password }
    - secretKey: JWT_SIGNING_KEY
      remoteRef: { key: dau-dx-api/prod/jwt, property: signing-key }
```

### 6.4 Vault Transit (사용자 DB 비밀번호)
- 등록 시: `vault write transit/encrypt/dau-dx-api plaintext={base64}` → ciphertext 저장
- 사용 시: `vault write transit/decrypt/dau-dx-api ciphertext={...}` → 평문 복호화 후 풀 생성에 사용
- 키 회전: 주기적 `transit/keys/.../rotate`, ciphertext 자동 재암호화 가능

## 7. 통신 보안

### 7.1 외부 통신 (TLS)
- 모든 외부 진입은 HTTPS (TLS 1.2+)
- 인증서: cert-manager + Let's Encrypt 또는 사내 CA
- HSTS 헤더: `Strict-Transport-Security: max-age=31536000; includeSubDomains`

### 7.2 내부 통신
- K8s 내부 Service 간 통신은 ClusterIP (사설망)
- 권장: Istio/Linkerd mTLS (Phase 2)

### 7.3 보안 헤더 (Frontend)
```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'
Permissions-Policy: geolocation=(), microphone=(), camera=()
```

### 7.4 CORS
- 백엔드 `/admin/**`: Next.js 도메인만 허용 (사실상 동일 도메인)
- 백엔드 `/api/**`: `Access-Control-Allow-Origin: *` 가능 (외부 호출 허용)

## 8. 감사 로그 (Audit Log)

### 8.1 감사 필드 — 마스터(`_M`) vs 이력(`_L`) 분리

**마스터 테이블(`_M`) — 10개 컬럼 (변경 추적용)**

| 컬럼 | 설명 |
|---|---|
| REGID | 등록자 사용자 ID |
| REGDT | 등록일시 (TIMESTAMP) |
| REGIP | 등록자 IP |
| REGMENU | 등록 시 메뉴 ID |
| REGPGM | 등록 시 프로그램 ID |
| MODID | 수정자 |
| MODDT | 수정일시 |
| MODIP | 수정자 IP |
| MODMENU | 수정 시 메뉴 ID |
| MODPGM | 수정 시 프로그램 ID |

**이력 테이블(`_L`) — 2개 컬럼 (append-only, 수정 없음)**

| 컬럼 | 설명 |
|---|---|
| REGID | 작성자 (서비스 계정 또는 사용자 ID, 04 §FR1.6 `system` 가능) |
| REGDT | 작성일시 (자동 SYSDATE) |

> 이력 테이블은 INSERT-only 라 MOD* 5개 + REGIP/REGMENU/REGPGM 3개는 의미 없다. NFR2.8 의 "모든 변경 작업"은 마스터 한정으로 해석한다. 본 분리는 06 §2.9 `DXAPI_CALL_HIST_L` 의 "(감사) REGID, REGDT (자동)" 표기와 일치한다.

### 8.2 자동 주입 (Spring AOP / MyBatis Interceptor)

```java
    }
}
```

### 8.3 인증 실패 로그
- 모든 4단 검증 실패는 별도 로그 + 메트릭 (`dxapi_auth_fail_total{reason}`)
- 동일 IP 분당 10회 실패 → 자동 차단 (Redis Counter + IP block list)

## 9. OWASP Top 10 점검

| OWASP | 본 시스템 대응 |
|---|---|
| A01 Broken Access Control | JWT 권한 체크, `/admin/**` 정책, 본인 자원만 접근 |
| A02 Cryptographic Failures | TLS 1.2+, bcrypt 12, HMAC SHA-256, Vault Transit |
| A03 Injection | Prepared Statement, SQL 화이트리스트, EXPLAIN 검증 |
| A04 Insecure Design | 본 PRD 보안 모델 + 4단 검증 + Audit |
| A05 Security Misconfiguration | distroless 이미지, root 금지, 보안 헤더, 시크릿 외부화 |
| A06 Vulnerable Components | Trivy 스캔 (Harbor), Dependabot, SBOM |
| A07 Identification and Authentication Failures | JWT + Refresh 회전, 로그인 실패 잠금 |
| A08 Software and Data Integrity Failures | Cosign 이미지 서명, GitOps 변경 감사 |
| A09 Security Logging and Monitoring Failures | OTel + Loki + 인증 실패 알람 |
| A10 SSRF | 외부 호출 없음. 데이터소스 URL 화이트리스트 |

## 11. 보안 점검 자동화

### 11.1 CI 단계
- **컨테이너 스캔**: Trivy (Harbor), High/Critical 발견 시 fail
- **의존성 스캔**: OWASP Dependency-Check (백엔드), `npm audit` (프론트엔드 — `package-lock.json` 이 단일 진실 공급원이므로 npm 만 게이트로 사용. 근거 [03 §5.1](03_시스템_아키텍처_설계서.md#51-프론트엔드-패키지-매니저-정책-bunnpm-분리))
- **SAST**: SonarQube (선택), GitLeaks (시크릿 검출)
- **시크릿 스캔**: gitleaks pre-commit hook + Gitea Actions

### 11.2 런타임
- **K8s**: NetworkPolicy 강제, PodSecurityStandards `restricted`
- **Falco**: 비정상 시스템 콜 감지 (선택)
- **Kyverno**: 이미지 서명 강제 (Cosign + ImageVerify), root 금지 정책 — 정책 정의는 [10 §5.4](10_CICD_및_운영_가이드.md#54-cosign-이미지-검증-kyverno). prod/stg = Enforce, dev = Audit. 분기 1회 DR 시나리오 C 로 재검증 ([10 §10.3](10_CICD_및_운영_가이드.md#103-dr-훈련-분기-1회))

### 11.3 정기 점검
- 분기 1회 모의 침투 테스트
- 월 1회 의존성 업데이트 + 재배포
- 주 1회 감사 로그 리뷰
