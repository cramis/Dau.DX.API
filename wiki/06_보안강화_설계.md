**작성일**: 2026-06-01 · **상태**: 설계(착수 전) · **선행**: [`01_본개발_PRD.md`](01_본개발_PRD.md), [`05_frontend_BFF_이관_로그.md`](05_frontend_BFF_이관_로그.md)

## 0. 왜 이 문서가 필요한가 (본질 연결)

이 프로젝트의 본질은 **"내부 DB 데이터를 코딩 없이 SQL 등록만으로 REST API 화하고, 외부 시스템에 인증·IP·기간·마스킹으로 통제해 *안전하게* 노출하는 게이트웨이"** 다. 가치는 두 축.

- **축A. 셀프서비스 API 제작** — DS·SQL·파라미터·응답 등록만으로 API 생성.
- **축B. 통제된 안전 노출** — 인증·IP·기간·매핑 검증 + 마스킹 + 이력.

현재까지(1차 + BFF 이관 + P2 일부) **기능 골격은 본질에 충실**하다. 게이트웨이 파이프라인·메타 등록·승인→매핑·호출이력은 정확히 구현됐다. 그러나 **축B(안전)의 깊이가 얕다.** 그리고 그것은 우연이 아니라 1차 범위에서 의도적으로 보류된 항목(open-questions C4/C6/C7)이다.

문제는 — 이 보류 항목들이 "있으면 좋은 것"이 아니라 **이 시스템의 존재 이유(안전한 PII 노출)를 충족하기 위한 필수 요건**이라는 점이다. 응답은 마스킹하면서 요청 PII 는 평문으로 이력에 남기면, 시스템 자체가 유출 지점이 된다. 외부에 DB 를 여는데 등록 SQL 의 파괴성 통제가 없으면, 게이트웨이가 공격 표면이 된다.

따라서 다음 작업은 import 같은 편의기능보다 **안전 축 보강이 본질상 먼저**다. 이 문서는 그 보강 항목 각각의 **목적(왜 필요한가)과 대응방법(어떻게 할 것인가)** 을 착수 전 합의하기 위함이다.

## 2. 갭#1 — 요청 파라미터 PII 마스킹 (이번 범위)

### 목적 (왜)
호출이력 `DXAPI_CALL_HIST_L.PARAM_JSON_TEXT` 에 외부가 보낸 요청 파라미터가 **원본 그대로** 저장된다. 외부 시스템이 주민번호·계좌·전화 등을 파라미터로 넘기면 그 PII 가 평문으로 이력에 영구 적재된다. 응답은 컬럼 마스킹(`MaskingApplier`)하면서 요청은 안 하므로, **마스킹의 절반이 비어 있다.** "PII 안전 노출"이 본질인 시스템에서 이력 테이블 자체가 유출 지점이 되는 것은 본질 위반급 결함이다. (PRD §9 "PARAM_JSON 은 PIPA 마스킹 적용 후 저장" 명시 → 미이행. open-q C6.)

### 현재
- `GatewayService.toJson(params)` → `objectMapper.writeValueAsString(params)` 원본. 주석 "PIPA 마스킹은 C6 후속. 현재는 원본 저장."
- `MaskingApplier` 는 응답 컬럼에만 적용. 규칙 7종(none/name/phone/email/rrn/card/addr) 보유 — **재사용 가능**.
- API 파라미터 메타(`DXAPI_API_PARAM_M`, FE `ApiParam`)에는 마스킹 규칙 필드가 **없다**(응답 `ApiResp` 에만 `maskRule` 존재).

### 대응 (어떻게)
어느 파라미터가 민감한지 알아야 마스킹한다. 두 경로를 결합한다.

1. **명시 메타(주)** — API 파라미터 정의에 `maskRule` 추가.
   - DDL. `DXAPI_API_PARAM_M` 에 `MASK_RULE_DVCD` 컬럼 추가(기본 'none'). → [`07_DBA_DDL.sql`] + [`06_DB_모델링.md`] 동기화 필수([[keep-ddl-with-backend]]).
   - DTO/매퍼. `ApiParamDto`/`ApiParamRow` + FE `ApiParam`(types/api.ts) + ApiForm 파라미터 행에 maskRule 선택 추가.
2. **휴리스틱(보조·안전망)** — 메타에 규칙이 없어도 값 패턴으로 자동 마스킹. 주민번호(`\d{6}-\d{7}`)·카드(`\d{4}-\d{4}-...`) 등 고위험 패턴만 보수적으로.
3. **적용 지점** — `GatewayService.record()` 직전, params 를 `MaskingApplier` 로 마스킹한 사본을 만들어 `toJson`. 원본 params 는 SQL 실행에만 쓰고, **이력엔 마스킹본만**.

> 설계 선택. param maskRule 메타가 정공법(정확·명시적). 휴리스틱은 메타 누락 시 안전망. 우선 휴리스틱+적용지점만으로 즉시 1차 방어, 메타 컬럼은 같은 PR 또는 직후.

### 검증
- 단위. `MaskingApplier` 파라미터 마스킹(주민번호→`******-*******` 등) 케이스.
- 端-端. 민감 param 으로 게이트웨이 호출 → `call_hist.PARAM_JSON` 에 마스킹값 확인. 실 SQL 실행 결과는 영향 없음(원본으로 실행).

### 범위 / 리스크
- 스키마 변경(param maskRule) → DDL 동기화 규칙 준수. 기존 param 은 'none' 기본 → 하위호환.
- 휴리스틱 과도 마스킹 위험 → 보수적 패턴만, 메타 우선.

### 체크리스트
- [x] `MaskingApplier.maskParamsForLog(params, ruleByParam)` + 단위테스트 (#1a)
- [x] `GatewayService.record` 가 마스킹본으로 `toJson` (원본은 실행에만) (#1a)
- [x] 휴리스틱 고위험 패턴(주민/카드) 안전망 (#1a)
- [ ] `DXAPI_API_PARAM_M.MASK_RULE_DVCD` 추가 — 07 DDL + 06 모델 동기화 (#1b)
- [ ] `ApiParamDto`/`ApiParamRow`/FE `ApiParam`/ApiForm 에 maskRule 반영 (#1b)
- [x] #1a 端-端 검증(call_hist 마스킹) / [ ] #1b 端-端 + 가이드(04) 갱신

## 3. 갭#2 — 등록 SQL 동사 화이트리스트 (이번 범위)

### 목적 (왜)
축A 는 "관리자가 SQL 을 등록"한다. 그런데 등록 SQL 의 **동사·구조에 제한이 없다.** `#{param}` 바인딩으로 파라미터 인젝션은 막지만, 등록 SQL 자체가 `DELETE FROM ...`·`DROP TABLE ...`·다중 스테이트먼트여도 막는 장치가 없다. `SqlExecutor` 는 SELECT vs update 분기만 하므로 DML 은 그대로 실행된다. 외부에 DB 를 여는 게이트웨이에서 **등록 SQL 의 파괴성 통제 부재는 핵심 공격 표면**이다. 실수든 악의든 한 줄로 대상 DB 를 훼손할 수 있다. (open-q C4 "SQL 화이트리스트 동사 집합" 미정.)

### 현재
- `SqlExecutor.execute` — `verb = sql.split[0]`; SELECT → query, 그 외 → `update`. 동사 검증 없음.
- `ApiDefService.validate` — method/status/param type/maskRule 만 검증. SQL 내용 미검증.
- `SqlValidationService`(validate-sql) — prepare 검증만(동사 무관).

### 대응 (어떻게)
1. **허용 동사 집합 정의(C4 닫기).** 기본 **SELECT only**(읽기 게이트웨이가 본령). 쓰기가 필요한 API 는 정의에 **명시 플래그**(예: `writeAllowed=Y`)가 있을 때만 `INSERT`/`UPDATE` 허용. `DELETE`·DDL(`DROP/ALTER/TRUNCATE/CREATE`)·`MERGE`·`GRANT` 등은 항상 거부.
2. **다중 스테이트먼트 차단.** 문자열 리터럴 밖의 `;` 로 분리되는 2개 이상 statement 거부(주석 `--`/`/* */` 트릭, `;` 위장 포함 보수적 파싱). 단일 statement 강제.
3. **3중 적용** — (a) API 등록/수정 `ApiDefService.validate` 에서 거부(`ErrorCode.INVALID_INPUT` 또는 신규 `SQL_NOT_ALLOWED`), (b) `validate-sql` 에서 동일 검사(폼서 즉시 피드백), (c) 런타임 `SqlExecutor` 에서도 방어(이중 안전망 — 우회 등록 대비).

> 설계 선택. 화이트리스트(허용만 통과)가 블랙리스트보다 안전. 동사 판정은 선두 토큰 + 금지 키워드 스캔 + 세미콜론 카운트의 조합. 완벽한 SQL 파서는 과投資 → 보수적 규칙으로 거부 우선(애매하면 막음).

### 검증
- 단위. `SELECT` 통과 / `DELETE`·`DROP`·`SELECT ...; DELETE ...`·주석트릭 거부. writeAllowed=Y 시 `INSERT`/`UPDATE` 통과, `DELETE` 여전히 거부.
- 端-端. 금지 SQL 등록 시도 → 거부. validate-sql 동일 거부. 기존 정상 API(SELECT) 회귀 통과.

### 범위 / 리스크
- 스키마 변경 없음(검증 로직). `writeAllowed` 플래그 도입 시 소폭(API 정의에 boolean — 기존 SELECT API 영향 없음, 기본 N).
- 과도 차단 위험 → 정상 SELECT/CTE/조인은 허용. WITH(CTE) 선두 토큰 예외 처리 주의.

### 체크리스트
- [x] 허용 동사·금지 키워드·다중스테이트먼트 규칙 정의(C4) → `gateway/SqlPolicy.check(sql, allowWrite)`
- [x] `ApiDefService.validate` 에 SQL 검증 추가(등록/수정 거부, method 기반)
- [x] `SqlValidationService` 에 동일 검사(폼 피드백, method 전달)
- [x] `SqlExecutor` 런타임 방어(관대 모드 하드가드)
- [x] ~~writeAllowed 플래그~~ → **HTTP method 기반**으로 대체(GET=읽기, 非GET=쓰기). 신규 필드 불필요
- [x] 단위(`SqlPolicyTest` 11종)/端-端 검증 + 가이드(04) 갱신

## 4. 로드맵 (설계만 — 후속)

### 갭#3 — DB 비밀번호 암호화
- **목적.** `DB_ENC_PW` 평문 저장 → MetaDB 유출 시 대상 DB 직접 침해. 인증키는 HMAC 해시인데 DB 자격증명만 평문인 비대칭.
- **대응.** 완전책은 Vault(C7). 그 전 경량 단계 — 앱 마스터키(env)로 **AES-GCM 대칭 암호화** 저장/복호(create·update·`DataSourceRegistry` 경유). 기존 평문 → 암호문 마이그레이션 스크립트.
- **범위.** 값 형식 변경. 마스터키 관리(env→후속 Vault).

### 갭#4 — 레이트리밋 / 쿼터
- **목적.** 한 연계시스템의 폭주가 대상 DB 커넥션을 고갈 → 전체 가용성 붕괴. "안전 노출"의 가용성 축.
- **대응.** 연계시스템별(또는 API별) 분당/일 한도. A5 정합(Redis 미사용) → in-process 슬라이딩 윈도우(단일 인스턴스) 또는 Oracle 카운터. 초과 시 `429` + 신규 `ErrorCode.RATE_LIMITED`. 한도는 연계시스템 메타 컬럼.
- **범위.** 메타 한도 컬럼 + 카운터. 중간.

### 갭#5 — 셀프서비스 신청 입구
- **목적.** 승인(승인/반려)은 실DB인데 **신청 생성**(회원가입·API 사용신청)이 백엔드에 없어 mock. 거버넌스 루프의 "사용자 신청" 절반이 빠짐 → 본질의 "셀프서비스"가 관리자 수동 등록에 의존.
- **대응.** `POST /api/auth/signup`(PENDING 사용자 + USER_SIGNUP 승인 생성), API 사용신청 엔드포인트(API_USAGE 승인 생성). 기존 승인 흐름과 결합 + BFF 연결.
- **범위.** 엔드포인트 신규 + BFF. 스키마 무변경(기존 테이블 활용).

## 6. 진행 로그 (시간순)

### 2026-06-01 — 갭#2 SQL 화이트리스트 ✅

**설계 조정**: 기존 쓰기 API 확인 결과 `A20260509003`(POST)=INSERT, `A20260509005`(POST)=`CALL sp_send_notification(...)`(저장프로시저). CALL 막으면 기존 API 깨짐 → 동사 정책을 **HTTP method 기반**으로 확정.
- GET → `SELECT/WITH`. 非GET → `SELECT/WITH/INSERT/UPDATE/MERGE/CALL`.
- 항상 거부: `DROP/TRUNCATE/ALTER/GRANT/REVOKE/RENAME/DELETE` + `DBMS_/UTL_` + 다중 스테이트먼트.

**변경 파일**
- `gateway/SqlPolicy.java`(신규) — `check(sql, allowWrite)`. 문자열/주석 제거 후 동사·다중문·금지토큰 검사.
- `apidef/ApiDefService.validate` — 등록/수정 시 `check(sql, method!=GET)` 거부.
- `apidef/SqlValidationService` + `ValidateSqlRequest`(+method) + `ApiDefController` + FE `ApiForm.validateSql`(method 전달) — 폼 즉시 피드백.
- `gateway/SqlExecutor.execute` — 런타임 하드가드(`check(sql, true)`).
- `gateway/SqlPolicyTest`(11종).

**검증 (실 dev Oracle)**
